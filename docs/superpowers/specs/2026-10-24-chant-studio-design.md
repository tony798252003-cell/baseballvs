# 應援曲工作台（Chant Studio）設計規格

**日期：** 2026-10-24
**功能：** 一個在本機執行的「應援曲工作台」：自動替缺歌的球員找 YouTube 版本、下載、自動切出前奏版／循環版，使用者在同一頁逐位試聽、拖拉微調切點與音量、標記「已解決」，最後一次上傳 Dropbox 並寫入資料庫。另含：舊歌音量統一、app 播放改為無縫接續。

---

## 背景與目標

使用者目前做一首應援曲的流程（2026-07-23 音樂流程改版之後）：在 YouTube 找版本 → 下載 → 自己剪前奏與循環 → `scripts/add-player-song.mjs` 上傳寫入。使用者說最花時間的是：

- **找乾淨的版本**：官方有就用官方，沒有才用現場錄的；現場版常錄到一半中斷、或被歡呼聲蓋掉。
- **切前奏**很煩：一首常有好幾段，有時要把幾段接起來當循環。
- **接縫順不順**要自己反覆按播放鍵確認。
- **音量**各首不一致（新舊歌都有）。

現況數字（2026-10-24，現役、非教練）：中職一軍 72/178 有歌（缺 106）、二軍 34/291、美職 0/18、日職 0/1066。使用者決定**先補中職一軍的野手**。投手登場曲（使用者原本希望有就補）因 app 只在打擊時播歌、且試驗中 11 位投手全搜不到，使用者決定**這次不補**，播放時機（換投時播）併入之後的「遊戲模式重新設計」討論。

### 試驗（spike）得到的事實

在 `/private/tmp/.../scratchpad/chant-spike/`（樂天桃猿一軍缺歌 17 位）實測：

- 在本機抓 `https://www.youtube.com/results?search_query=…` 並解析 `ytInitialData` 可取得標題、長度、頻道、觀看數、videoId（不需 API key）。下載用 yt-dlp（已用 `uv tool install yt-dlp` 安裝在 `~/.local/bin/yt-dlp`；Homebrew 因 Command Line Tools 過舊而失敗）。
- 17 位只找到 5 位（野手）；**11 位投手全找不到**（登場曲多半是流行歌，YouTube 標題不會掛球員名字）；邱勝宥找不到。
- 版本類型：球團官方頻道（多為現場錄）、球迷現場直拍（最多、常中斷有雜音）、整理過的短版（最乾淨）、交響樂／Remix 改編版（乾淨但旋律不同）。
- **自動切點不可靠**：應援曲以鼓、銅管、吶喊為主，自相似度低（0.27–0.43）。使用者試聽：只有林禹叡接得好，其他都不對。
- 使用者既有成品的結構（陳鏞基，比對取樣完全一致）：**前奏版 = 開頭→B、循環版 = A→B**，A 為前奏結束／循環起點，B 為循環終點。因此「前奏→循環」與「循環→循環」是**同一個接縫（B 跳回 A）**。
- 試驗頁的拖拉微調（波形＋A/B 兩條線＋兩張 ±1.5 秒放大圖＋±0.01/±0.1 秒按鈕＋對齊鼓點＋淡入淡出滑桿＋放開自動播接縫＋紅色播放線＋雙擊從該處播原曲）使用者評價「拖拉不錯」，並要求看得到播放位置（已加）。

### 目標

- 把「找版本→下載→切→試聽→上傳→入庫」變成一頁逐位處理，使用者只負責「聽」和「必要時拖一下」。
- 卡片上聽到的就是最終成品（預覽＝成品）。
- 新舊歌音量一致。
- app 裡前奏接循環、循環接循環沒有空白。

### 非目標

- 自動判斷哪個版本「最乾淨」到不需人工試聽——一定保留人工確認。
- 二軍、美職、日職的批次補歌（工具要能用參數指定範圍，但這次只跑中職一軍）。
- 投手登場曲：這次不補、不搜尋；換投時播登場曲的功能留待遊戲模式重新設計。工作台預設排除 `main_position` 為投手（P/SP/RP/CP）的球員，可用 `--include-pitchers` 覆寫（之後用）。
- 去人聲／去觀眾聲的 AI 處理。
- 後台（AdminScreen）裡的工作台按鈕——工作台在本機跑，由 Claude 啟動。

### 反目標

- 覆蓋任何已經有歌的球員的 `song`／`intro`（舊歌音量統一是另一個明確動作，見 §5）。
- 預覽聽起來順、成品或 app 裡卻有空白或音量跳動。
- 未經使用者按「已解決」就上傳或寫入。
- 弄丟 Dropbox 上的舊檔（覆蓋前必須先備份）。

## 範圍

### 1. 工作台的執行方式

- 一支本機 Node 程式（例：`scripts/chant-studio.mjs`），啟動一個只綁 `127.0.0.1` 的小型 HTTP 伺服器，提供卡片頁與後端動作（搜尋、下載、算建議切點、產生成品、上傳）。瀏覽器不能跑 ffmpeg／yt-dlp，所以需要這個後端。
- 參數指定範圍，至少：`--team <隊名>`（可多個）、`--league 一軍|二軍`、`--org CPBL|NPB|MLB`；預設只列 `status='active'`、非教練、**`song` 為空**的球員。
- 進度存本機狀態檔（例：`scripts/.cache/chant-studio/<批次>.json`，已在 `.gitignore`），關掉再開可接續；下載的原曲與成品也放在 `scripts/.cache/chant-studio/` 下。
- 沿用現有：`scripts/lib/env.mjs`（Supabase service client、`.env`）、`scripts/lib/dropboxMusicSync.mjs`（`uploadToDropbox`、`getSharedLinkRawUrl`）、ffmpeg（`~/bin/ffmpeg`，以 PATH 或環境變數找）、yt-dlp（PATH 或 `~/.local/bin/yt-dlp`）。
- **Dropbox 長期授權（使用者要求）**：Dropbox 產生的 access token 約 4 小時過期，改用 refresh token：
  - `.env` 新增 `DROPBOX_APP_KEY`、`DROPBOX_APP_SECRET`、`DROPBOX_REFRESH_TOKEN`（名稱寫進 `.env.example`）。
  - 一次性設定 script（例：`scripts/dropbox-auth.mjs`）：印出 `https://www.dropbox.com/oauth2/authorize?client_id=<key>&token_access_type=offline&response_type=code` 讓使用者開啟授權，使用者貼回授權碼，script 換取 refresh token 並**直接寫入 `.env`**（不印出 token）。
  - `scripts/lib/dropboxMusicSync.mjs` 新增取得 access token 的函式：有 refresh token 就用 `https://api.dropboxapi.com/oauth2/token`（`grant_type=refresh_token`）換短期 token 並快取到過期前；沒有才退回 `DROPBOX_TOKEN`。既有使用 `DROPBOX_TOKEN` 的 script 改走這個函式。
  - App 權限需要 `files.content.read`、`files.content.write`、`sharing.read`、`sharing.write`。
  - 後台 AdminScreen 的 Dropbox token 輸入框維持現狀（不在範圍內）。

### 2. 找版本

- 每位球員搜尋 YouTube：用「`<隊名> <姓名> 應援曲`」「`<姓名> 應援曲`」。請求間隔 ≥1.5 秒。
- 排序規則（沿用試驗並可調）：標題須含姓名；長度 0:30–3:00 加分；整理過的短版與球團官方頻道加分；「交響樂／Remix／改編／cover／鋼琴／直笛／教學」、多人合輯、啦啦隊直拍（cheerleader、fancam、#shorts、女孩團名）扣分；觀看數高加分。
- 每位保留前 3 名候選。預設採用第 1 名並下載；**卡片上可「🔄 換下一個版本」**改用第 2、3 名。
- **找不到或都不對時，卡片提供「貼 YouTube 網址」欄位**（Claude 的決定），貼上後下載並處理。

### 3. 卡片（同一頁，每位一張）

狀態：`待處理`／`✅ 已解決`／`⏭ 跳過`／`找不到`。頁面頂部顯示各狀態數量與篩選。

每張卡片內容：
- 球員（背號、姓名、守位）、採用的影片（標題、頻道、長度、連結）與挑選理由、候選 2、3 名。
- **成品試聽**：`▶ 前奏→循環×2`（有前奏時）、`🔁 循環×3`、`⏩ 只聽接縫（B 前 3 秒 → A 後 3 秒）`、`■ 停止`。皆以 Web Audio 無縫排程播放。
- **微調區**（沿用試驗頁的互動，使用者已認可）：
  - 整首波形＋A（綠）、B（橙）兩條可拖拉的線；A、B 各一張 ±1.5 秒放大圖可拖拉；波形底部顯示偵測到的鼓點。
  - A、B 各有 −0.1／−0.01／+0.01／+0.1 秒按鈕與「對齊鼓點」。
  - **紅色播放線**同步顯示在三張波形上，旁邊顯示目前秒數；雙擊整首波形＝從該處播原曲。
  - 放開拖拉或按微調按鈕後自動播放接縫。
  - 淡入淡出長度滑桿 0–300 ms。
  - 「有前奏」勾選（使用者規則 B：只有開頭明顯有前奏時才做前奏版；自動判斷前奏 ≥2 秒才預設勾選）。
  - **音量滑桿 −6～+6 dB**（套用在自動統一響度之後），預覽即時套用。
- 動作按鈕：`✅ 此筆已解決`、`🔄 換下一個版本`、`⏭ 跳過`、貼網址欄位。
- 卡片的 A／B／淡入淡出／前奏勾選／音量／採用影片 都存進狀態檔。

### 4. 預覽＝成品（音訊處理規則）

- 下載後先把**整首原曲**做一次響度量測（EBU R128，單位 LUFS），算出把它調到目標響度所需的增益；之後的預覽與成品都套用「這個增益＋卡片音量滑桿」。前奏版與循環版因為來自同一首、同一個增益，接縫處不會有音量跳動。
- 目標響度：以**現有舊歌的響度中位數**附近為準（實作時先量測 Dropbox 上現有檔案再定一個固定值，寫進設定常數）。**定案：−12 LUFS**（使用者 2026-10-24 決定；量測結果循環版中位數 −12.6 LUFS）。
- 成品：
  - 前奏版（有前奏時）＝原曲 0 → B，結尾淡出。
  - 循環版＝原曲 A → B，頭尾各套淡入淡出（長度＝滑桿值）。
  - 輸出 mp3；為了無縫接續，需避免 mp3 編碼器在檔頭補的空白造成縫隙（例如用 ffmpeg 正確寫入 gapless 資訊，或改輸出不會補空白的格式如 AAC/M4A；實作者選一種並在 app 播放端一併驗證）。
- 卡片上的預覽用瀏覽器直接對「原曲＋增益＋A/B＋淡入淡出」做排程播放，邏輯與成品產生完全一致；產生成品後，卡片的試聽改播放產生出來的實際檔案（實作者決定在按「已解決」時產生，或在送出時產生並允許重聽）。

### 5. 送出與舊歌音量統一

- 頂部「📤 送出已解決的」：對所有 `✅` 的卡片產生成品 → 上傳 Dropbox `/Music/Players/` → 取得 `?raw=1` 連結 → 寫入 `players.song`（與 `intro`，若有前奏）。檔名沿用 2026-07-23 規格：`球隊 - 姓名.mp3`、`球隊 - 姓名 - Intro.mp3`（副檔名隨 §4 的格式決定）。
- 寫入前再檢查一次該球員 `song` 仍為空；不是空的就跳過並列出（避免覆蓋）。
- 結束印出摘要：上傳幾首、跳過幾首、失敗清單。
- **舊歌音量統一**（另一個明確指令，例：`--normalize-existing`）：
  1. 先把 Dropbox `/Music/Players/` 及資料庫中所有被 `song`／`intro` 引用的 Dropbox 檔完整下載到本機備份目錄（repo 外，例：`/Users/tonywang/orca/workspaces/baseballvs/backups/music-<日期>/`），並記錄檔名↔球員對照。
  2. 量測每首響度；同一位球員的前奏版與循環版**用同一個增益**（以循環版量測值為準）。
  3. dry run 先列出每首目前響度與將套用的增益，使用者確認後才覆蓋上傳（同路徑覆蓋，分享連結不變則資料庫不必改；若連結會變，一併更新資料庫）。
  4. `team_chants`（嗆斯曲）與通用應援曲也套用同一目標響度（使用者沒特別提，Claude 的決定；成本低且讓整體一致）。

### 6. app 播放改為無縫

- `src/composables/useAudio.js` 目前用 `<audio>` 的 `onended` 換 `src`，前奏→循環、循環→循環都會有空白。改為 Web Audio API：預先解碼 intro 與 song，前奏播完在精確時間點排程循環版，循環版用 `loop`（AudioBufferSourceNode.loop）或連續排程。
- 既有行為保留：嗆斯曲／接手球隊嗆斯曲／通用應援曲的備案順序、暫停／繼續、靜音、換打者時停止前一首。
- 行動裝置需在使用者第一次點擊後 `resume()` AudioContext（沿用現有「Auto-play prevented」的處理精神）。
- Dropbox `?raw=1` 連結需允許 `fetch` 取得音訊資料（CORS）；實作者先驗證，若不允許則保留 `<audio>` 備案並在報告中說明。

## 驗證方式

- **工作台**：`node scripts/chant-studio.mjs --team 樂天桃猿 --league 一軍` 開出 6 張卡片（樂天一軍缺歌 17 位扣掉 11 位投手）；換版本、貼網址、拖拉、播放線、音量滑桿、已解決／跳過狀態在重開後保留。
- **預覽＝成品**：同一位球員，卡片預覽的接縫與產生出的實際檔案用同一組播放按鈕聽起來一致；以程式比對：成品循環版的長度＝B−A（容許編碼誤差 <10 ms）、前奏版＝B。
- **不覆蓋**：送出時若資料庫 `song` 已非空，該筆被跳過且列出。
- **舊歌統一**：備份目錄檔案數＝被引用的檔案數；dry run 列出響度；套用後重新量測，全部落在目標 ±1 LU 內；同一球員前奏與循環的增益相同。
- **app 無縫**：在 app 實際播放一位有前奏的球員，前奏→循環、循環→循環無可聽見空白；暫停／繼續、換打者、備案嗆斯曲仍正常。
- 純邏輯（排序規則、切點→ffmpeg 參數、增益計算、狀態檔讀寫）以 `node --test` 測試。

## Claude 的決定（builder check 後補充，使用者可推翻）

- **格式固定 mp3**：既有腳本（`dropboxMusicSync.mjs` 的檔名解析、`migrate-legacy-songs.mjs`）與各瀏覽器相容性都以 mp3 為準。用 ffmpeg/LAME 寫入 gapless 資訊（encoder delay/padding），並在 app 播放端以實測確認無縫；若某瀏覽器仍有縫隙，app 端依 LAME 標頭修剪前後補白。§4、§5 的「副檔名隨格式決定」一律為 `.mp3`。
- **舊歌音量統一時一併重新編碼**（高品質，如 LAME V0），同時修掉舊檔的編碼補白；原檔已完整備份，所以可接受一次有損重編碼。
- **Dropbox 同路徑覆蓋**預期分享連結不變；實作時以一首實測確認，若連結改變，同步更新資料庫中所有引用。
- **intro 欄位規則**：工作台只處理 `song` 為空的球員。已有非空 `intro`（文字 TTS 或音檔）一律不覆蓋；若此時又切出前奏版，略過前奏版並在摘要列出。「有前奏」未勾選時不動 `intro`。（2026-10-24 查：中職一軍缺歌的 106 位中，0 位有 intro。）
- **範圍篩選**：`status='active'`、`is_coach=false`、`song` 為空；`--org` 預設 `CPBL`，`--league` 只對 CPBL 生效。
- **目標響度**：**−12 LUFS**（使用者 2026-10-24 決定，取代原本 −14 LUFS 的佔位值；依據為量測舊歌，含 `team_chants` 表與 `app_settings.generic_chant_url`，循環版中位數 −12.6 LUFS）。純增益（ffmpeg `ebur128` 量測＋`volume`），加真峰值限制（−1 dBTP）防爆音；淡入淡出用線性。
- **預覽＝成品的驗證標準**：長度誤差 <10 ms＋人工試聽，不要求取樣級一致。
- **YouTube 擋爬或 yt-dlp 失敗**：卡片顯示錯誤並允許重試；必要時用 `--cookies-from-browser chrome`。只用 ffmpeg，不需 ffprobe。
- **狀態檔與下載位置**改放 repo 外的持久目錄：`/Users/tonywang/orca/workspaces/baseballvs/chant-studio/`（worktree 刪掉也不會遺失）。批次名稱由 `--team`/`--league` 組成，也可用 `--batch` 指定。
- **app 無縫播放**：若 Dropbox 連結不允許 `fetch`（CORS），保留 `<audio>` 播放作為備案；實作者需檢查 `audioRef` 在 `App.vue` 以外的使用處。不設歌曲長度上限（應援曲 <3 分鐘）。

## 留給實作者決定

- 自動建議切點的演算法（試驗版的自相似度法不可靠；可改為先偵測拍點、只在整數小節長度找循環）。建議值只是起點，人工拖拉為主。
- 伺服器與前端的檔案拆分、API 形狀、頁面樣式（沿用試驗頁的互動即可，不需視覺設計）。
- §4 的無縫格式選擇（mp3 gapless 或 m4a）。
- 何時產生實際成品檔（按已解決時或送出時）。
- 目標響度的實際數值（量測舊歌後決定）。
